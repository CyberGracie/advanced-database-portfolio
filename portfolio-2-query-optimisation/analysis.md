# Performance Analysis – NairaFlow Digital Bank

## 1. Method

- **Environment:** PostgreSQL 18 on my Windows laptop, managed with pgAdmin 4.
- **Data volume:** 502,000 transactions, 300,000 transfers, about 772,000 ledger entries,
  2,000 accounts and 1,000 customers (generated by `seed.sql`).
- **Measurement:** each query was run with `EXPLAIN (ANALYZE, BUFFERS)` three times;
  the **median** execution time is reported, because single runs varied by up to 40%
  (background processes and caching on a laptop).
- **Control:** `VACUUM ANALYZE` was run before creating indexes, and Q1 was re-timed
  (341.660 ms, within its original 305–487 ms range). Vacuuming alone therefore did not
  cause the improvements below.
- Full plans: [`plans/before`](plans/before) and [`plans/after`](plans/after).
  Raw timings: [`timings.md`](timings.md).

## 2. Indexes created

| Index | Definition | Type | Target queries | Size |
| --- | --- | --- | --- | --- |
| I1 `idx_ledger_account_created` | `ledger_entries (account_id, created_at) INCLUDE (entry_type, amount)` | Composite, covering | Q1, Q5 | 52 MB |
| I2 `idx_transactions_failed_created` | `transactions (created_at) WHERE status = 'FAILED'` | Partial | Q2, Q6 | 344 kB |
| I3 `idx_transactions_created` | `transactions (created_at) INCLUDE (status, transaction_type, amount)` | Covering | Q3, Q4 | 25 MB |
| I4 `idx_transfers_source_account` | `transfers (source_account_id)` | Foreign-key index | Q3, Q6 | 2048 kB |

PostgreSQL automatically indexes primary keys and `UNIQUE` columns, but **not foreign keys**,
so I1 (led by the foreign key `account_id`) and I4 fill gaps a design review would otherwise flag.

## 3. Results

| Query | Before (ms) | After (ms) | Change | Plan before → after |
| --- | --- | --- | --- | --- |
| Q1 Account statement | 353.944 | 0.488 | **~725× faster** | Parallel Seq Scan → Index Scan (I1) |
| Q2 Failed transfers (1 day) | 216.375 | 0.656 | **~330× faster** | Parallel Seq Scan → Index Scan (I2) |
| Q4 Daily totals (1 month) | 366.663 | 92.998 | **~3.9× faster** | Parallel Seq Scan → Index Only Scan (I3) |
| Q6 Suspicious activity (1 month) | 278.890 | 117.848 | **~2.4× faster** | Parallel Seq Scan → Bitmap Index Scan (I2) |
| Q3 Top 10 customers (1 quarter) | 621.821 | 778.384 | No real change | Identical plan; no index used |
| Q5 Balance reconciliation (all rows) | 564.719 | 761.616 | No real change | Identical plan; no index used |

## 4. Findings

### 4.1 Highly selective queries gain the most (Q1, Q2)

Before indexing, Q1 read every ledger row (about 772,000; `Rows Removed by Filter: 257,385`
per worker × 3 workers) to return **38 rows**, touching about 15,000 pages. With I1 it reads
**34 pages** and finishes in under a millisecond. The column order matters:
`account_id` first narrows to one account, then `created_at` narrows to the date range,
and because the index stores entries in date order, the plan needs **no Sort step** for
`ORDER BY created_at`.

Q2 benefits from a **partial index**: I2 only contains failed transactions (about 5% of
transfers), so it is small and points directly at the rows operations staff investigate.

### 4.2 Moderately selective queries gain less (Q4, Q6)

Q4 and Q6 filter one month out of nine (about 11% of rows). The index avoids reading the
other eight months, but each matching row still has to be processed and aggregated, so the
gain is a few times rather than hundreds of times.

- **Q4 used an Index Only Scan on I3.** Because I3 stores `status`, `transaction_type` and
  `amount` alongside `created_at` (`INCLUDE`), all 50,200 September transactions were read
  from the index alone, without visiting the table. This is where the covering design paid off.
- **Q6 used a Bitmap Index Scan on I2.** PostgreSQL first collected the locations of all
  1,445 failed September transactions from the small partial index, then read those table
  pages in physical order. A bitmap scan is chosen when too many rows match for one-by-one
  index lookups to be efficient, but too few to justify reading the whole table.

### 4.3 Bulk queries do not benefit (Q3, Q5) – and the planner was right

For Q3 and Q5, the **after plans are identical to the before plans**, with the same estimated
costs (for example, `Parallel Seq Scan on ledger_entries (cost=0.00..18395.47)` in both),
so the indexes were not used and cannot be the cause of the slower medians. The before and
after ranges overlap (Q3: 562–837 ms before, 709–904 ms after), so the difference is
run-to-run variation on a laptop, not a real regression.

The planner skipped the indexes because these queries are not selective:
- Q3 matches about **162,000 of 502,000 transactions (~32%)**. Reading a table sequentially
  is cheaper than 162,000 separate index lookups.
- Q5 must total **every** ledger row to reconcile every account.

**Experiment:** to test this, I forced an index plan for Q5 with `SET enable_seqscan = off`
([plan](plans/after/q5-forced-index-plan.txt)). PostgreSQL used a **Parallel Index Only Scan**
on I1 with `Heap Fetches: 0`, reading about **4,650 pages instead of about 15,000**, yet it
took **635.763 ms**, no faster than the normal plan. The bottleneck in Q5 is not reading
data but **aggregating 772,000 amounts**, so reducing I/O does not help. The planner's
estimate (about 29,000 for the forced plan against about 23,500) correctly predicted this.

## 5. The cost of indexes

| Cost | Measurement |
| --- | --- |
| **Write speed** | Inserting 50,000 ledger rows took **1,947.782 ms** with no extra indexes and **3,785.701 ms** with I1 in place, about **94% slower**. Each insert must also be placed in the sorted index. Each figure is a single run, so the percentage is approximate. |
| **Storage** | The four indexes use about **79 MB** in total (52 MB + 25 MB + 2 MB + 0.3 MB; see `screenshots/index-sizes.png`). The partial index I2 is only **344 kB**, about **75× smaller** than I3 (25 MB), even though both index `transactions.created_at`, because I2 holds only failed transactions. I1 is the largest (52 MB) because it covers every ledger row and also stores two extra columns to enable index-only scans, a cost the Q5 experiment showed does not pay off for reconciliation. |
| **Foreign key checks** | Even before indexing, about 1,620 ms of the 1,948 ms insert was spent checking the two foreign keys on `ledger_entries` (shown as constraint triggers in the plan). Integrity has a write cost too. |

## 6. Recommendations

1. **Keep I1 and I2.** Statements and failure investigations run constantly; a 2× slower
   ledger insert is an acceptable price for 330–725× faster reads, because each account is
   read far more often than it is written.
2. **Keep I3 for reporting,** but review it in production: it made the monthly dashboard
   query an index-only scan, but adds write cost to every transaction.
3. **I4** supports joins and cascading checks from `accounts` to `transfers`; it was not
   chosen for these particular queries, so its value should be confirmed with real workload
   statistics (`pg_stat_user_indexes.idx_scan`).
4. **Reconciliation (Q5) needs a different approach, not an index:** reconcile only ledger
   entries since the last successful audit, or maintain a daily balance summary table, so
   each run processes thousands of rows instead of 772,000.
5. **For dashboards (Q4),** a materialised view refreshed nightly would make the query
   near-instant, at the cost of slightly stale data.

## 7. Limitations

- Timings come from a laptop with other software running; medians reduce, but do not remove, this noise.
- Seed data is uniformly random. Real banking data is skewed (a few very active accounts),
  which would change selectivity and possibly plan choices.
- The write test was run once before and once after indexing.
